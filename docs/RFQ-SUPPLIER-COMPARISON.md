# تقرير RFQ + Supplier Comparison Engine (PHASE 14/15)

## ملاحظة مهمة
عند بدء هاد المرحلة، تبيّن أن **الميزة كانت مبنية بالفعل بالكامل** (schema + backend service + backend tests + controller + frontend api-client + frontend modal + ربطها بصفحة `/purchases`) من عمل سابق. المهمة تحولت من "بناء من الصفر" إلى **تدقيق واكتمال**: حذفت الملفات المكررة اللي بنيتها بالخطأ قبل ما نكتشف الميزة موجودة، وتحققت من الربط الكامل بتشغيل فعلي للاختبارات والبناء.

## ما هو موجود فعلياً (تم التحقق منه بالتشغيل)

### محرك تقييم موردين حقيقي — ماشي مجرد سعر
`SuppliersService.compareForProduct()`:
- **الموثوقية محسوبة من التاريخ الحقيقي** (`computeReliability`) — نسبة الطلبات اللي وصلات فموعدها أو قبلو، من `PurchaseOrder` الحقيقية بحالة `RECEIVED`. مورد بلا تاريخ كيوخذ 100 (الاستفادة من الشك) لكن مع `sampleSize: 0` واضح باش الواجهة تبين "بلا تاريخ".
- **معادلة مركّبة**: 40% تكلفة + 30% موثوقية + 30% مدة تسليم — كل عامل مُطبّع نسبياً لأفضل عرض بين المتاحين.
- **مُختبر رقمياً بنفس مثال المواصفات/الديمو بالضبط**: NSK أرخص لكن موثوقيته ضعيفة وبطيء (38 يوم) → **لا يفوز**، رغم أنه الأرخص.

### تسجيل العروض (RFQ الفعلي)
`SuppliersService.addOffer()`: تسجيل/تحديث عرض سعر من مورد لمنتج معيّن (upsert — عرض جديد لنفس الزوج مورد+منتج يحدّث السعر بدل ما يكرره، يعكس السعر الحالي المتفاوض عليه).

### API
```
GET  /api/suppliers/comparison?productId=...  [purchases.view]
POST /api/suppliers/:id/offers                [purchases.create]
```

### Frontend
- زر "مقارنة الموردين" فصفحة `/purchases` يفتح `SupplierComparisonModal`
- اختيار منتج → جدول مقارنة حي (مورد، سعر، مدة تسليم، موثوقية، نتيجة مركّبة) مع تظليل "الأفضل"
- نموذج مدمج لإضافة عرض سعر مباشرة من نفس الـ modal

## القيود (موثقة فالكود نفسه)
- **بدون RFQ formal workflow** (حالات مثل DRAFT→SENT→RECEIVING_OFFERS→CLOSED) — النظام الحالي "كتالوج أسعار حي" لكل زوج مورد+منتج، يُحدَّث مباشرة، وليس دورة طلب-عروض رسمية بمواعيد نهائية. أبسط وأعملي، لكن ماشي مطابق 100% للـ workflow الرسمي المذكور فPHASE 14.
- **لا تحويل عملات**: إذا الموردين عندهم عروض بعملات مختلفة لنفس المنتج، المقارنة تبقى على الأرقام الخام بدون تحويل لعملة موحدة.
- **لا ربط مباشر "تحويل العرض الفائز لطلب شراء بضغطة واحدة"** — المستخدم يشوف "الأفضل" فالمقارنة، لكن خلق طلب الشراء يبقى خطوة يدوية منفصلة (`CreatePurchaseOrderModal`).
